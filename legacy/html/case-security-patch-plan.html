01 / PROBLEM AND SCOPE

보안 패치의 대상이
한 프로세스에만 있지 않았습니다

Java 취약점 CVE-2026-114938과 NGINX 점검 요청을 받았지만 변경 위치는 하나가 아니었습니다. TROMBONE 3.0.3에서 실행 중인 Jenkins와 SonarQube의 JVM, Jenkins 에이전트, Java 애플리케이션의 기반 이미지, React의 빌드 이미지와 서비스 이미지를 구분했습니다.

대상실행 위치변경 지점
Jenkins, SonarQube플랫폼에서 실행 중인 Java 프로세스Helm 값의 JVM 옵션 조정
Jenkins 에이전트 2대에이전트와 빌드 프로세스JVM 옵션과 JAVA_TOOL_OPTIONS 설정, 재연결
Java 애플리케이션컨테이너 이미지 빌드Jib 기반 이미지를 Amazon Corretto 17로 변경
React 애플리케이션Node 빌드 단계와 NGINX 서비스 단계두 단계의 기반 이미지를 각각 변경

02 / JVM OPTIONS

같은 JVM 옵션을
프로세스별 설정에 나눠 넣었습니다

Jenkins 컨트롤러에는 javaOpts를, SonarQube에는 Web, Compute Engine, Search 프로세스별 설정을 사용했습니다. SonarQube의 jvmOpts를 바꾸면 기본 힙 설정을 대체하므로 기존 -Xmx512m -Xms128m과 HeapDump 옵션을 함께 남겼습니다.

에이전트 2대는 JVM Options와 JAVA_TOOL_OPTIONS 변경 후 재연결하는 흐름으로 정리했습니다. 값 파일뿐 아니라 실행 중인 프로세스의 옵션도 확인하도록 했습니다.

03 / BASE IMAGES

빌드와 서비스의 기반 이미지를
각각 지정했습니다

Java 애플리케이션은 Jib의 기반 이미지를 Harbor의 Amazon Corretto 17 커스텀 이미지로 지정하는 변경안을 만들었습니다. React는 Node 이미지로 빌드하고 NGINX 이미지로 결과물을 서비스하므로 두 FROM을 각각 변경하도록 구성했습니다.

NGINX 공식 권고의 취약 범위와 교체 버전을 대조했습니다. 이미지 이름만으로 판단하지 않도록 Corretto와 Node의 실제 태그, 빌드 결과도 확인 항목에 넣었습니다.

Oracle Java 취약점 정보 NGINX 보안 권고 Node.js 24.22.3 릴리스

04 / RUNTIME VERIFICATION

설정 값이 실행 중인 JVM에
전달됐는지 확인하도록 설계했습니다

배포 순서는 Jenkins를 먼저 확인한 다음 SonarQube로 이어지게 구성했습니다. 롤아웃 완료만으로 옵션 반영을 판단하지 않고, 실제 Java 프로세스가 받은 플래그를 확인하는 명령을 함께 준비했습니다.

Jenkins는 VM.flags를 확인하고, SonarQube는 Web, Compute Engine, Search 프로세스의 시작 인자를 따로 봅니다. 에이전트는 재연결 후 시작 명령에 옵션이 붙었는지 확인합니다.
