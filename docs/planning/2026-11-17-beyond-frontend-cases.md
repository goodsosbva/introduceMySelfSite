# Beyond Frontend 두 번째 탭 개편 계획

## 현재 화면의 문제

- 세 카드가 모두 같은 세 단계 도식이라 작업마다 무엇이 달랐는지 보이지 않는다.
- 세 카드가 한 HTML 페이지의 짧은 구역으로 연결된다. 문제, 맡은 범위, 판단 근거와 확인 결과를 읽기 어렵다.
- `01`, `02`, `03` 번호와 Kubernetes 중심의 제목은 항목이 세 개로 끝나는 듯한 인상을 준다.
- 배포 대응을 했다는 사실은 보이지만, 프론트엔드 밖에서 무엇을 계속 배우고 만드는지는 드러나지 않는다.

## 두 번째 탭의 역할

탭 이름은 **Beyond Frontend**를 유지한다. 이 안에는 백엔드 개발, 자동화, 플랫폼 운영, 배포 대응과 개인 실험을 한 목록으로 쌓는다. 분야별 탭을 더 만들지 않는다.

항목의 기준은 기술 이름이 아니라 **직접 맡거나 시험한 문제 한 건**이다. 항목 하나에 카드 하나와 상세 페이지 하나를 둔다. 진행 중인 작업도 실제 코드나 확인 결과가 있으면 올리고, 카드에 `진행 중`을 표시한다. 작업이 늘어날 때마다 같은 형식으로 아래에 추가한다.

## 목록 화면

현재 사이트의 흰 배경, 남색 글자, 푸른색 포인트와 넓은 카드 간격을 유지한다. Beyond Frontend의 항목 수는 고정하지 않는다. 대표 사례 한 건만 기존 Frontend 카드처럼 가로로 크게 보여주고, 나머지는 넉넉한 간격의 2열 카드로 이어 간다. 모바일에서는 한 열이다. 대표 사례는 본인의 역할과 공개 자료가 가장 분명한 작업으로 선택하며, 새 작업이 생겨도 자동으로 바뀌지 않는다.

첫 화면에는 대표 사례를 포함해 최대 다섯 건을 보여준다. 여섯 번째부터는 `사례 더 보기` 버튼으로 네 건씩 펼친다. 다섯 건 이하일 때 버튼은 보이지 않는다. 카드가 늘어난다고 헤더나 분야별 탭을 추가하지 않는다. 대표 사례 아래의 카드는 최근 작업이 위에 오도록 정렬한다.

```text
Projects.
[ Frontend ] [ Beyond Frontend ]
최근에는 Kubernetes 운영과 배포 문제를 다루고 있습니다.

대표 사례: 실무 / PLATFORM                실제 배포 화면 또는 명령 결과 일부
폐쇄망 Kubernetes 이미지 패치           민감한 값은 가린다
어떤 제약에서 무엇을 바꿨는지 2문장
Kubernetes  Linux  Container Image      사례 자세히 보기 ↗

┌ 실무 / DEPLOYMENT ───────────────┐  ┌ 실무 / DOCUMENTATION ───────────┐
│ Argo CD 상태와 오류 로그 일부     │  │ 실행 가이드 일부                 │
│ GitOps 배포 복구                  │  │ 패치 가이드와 기술지원           │
│ 맡은 일과 확인 결과 2문장         │  │ 맡은 일과 확인 결과 2문장         │
│ 사례 자세히 보기 ↗               │  │ 사례 자세히 보기 ↗               │
└───────────────────────────────────┘  └───────────────────────────────────┘

새 작업은 위 카드들과 같은 2열 목록에 추가
여섯 번째부터 `사례 더 보기` 표시
```

카드에는 제목, `실무` 또는 `개인 탐구`, 분야 표기, 본인이 한 일 두 문장, 핵심 기술 두세 개만 둔다. 고정 번호와 전체 개수는 없앤다. 상세 페이지로 가는 링크는 카드 전체와 `사례 자세히 보기`에 모두 둔다. 새 사례의 분야가 백엔드, 자동화, 데이터 중 무엇이든 같은 카드 형식으로 추가한다. `BACKEND`, `AUTOMATION`, `PLATFORM`, `DATA`는 작은 분야 표기일 뿐, 별도의 필터가 아니다.

카드의 큰 이미지는 매번 같은 도식으로 채우지 않는다. 화면이 있는 작업은 캡처, 화면이 없는 작업은 실제 로그, 설정 일부, 문서 발췌 또는 아키텍처 그림을 쓴다. 그림의 캡션은 `배포 상태 확인`, `오류 로그`, `실행 가이드`처럼 자료 이름만 적는다.

## 상세 페이지: 한 작업에 한 페이지

현재 `case-beyond-frontend.html#...` 방식은 끝낸다. 각 카드는 독립 주소로 연결한다.

| 현재 카드 | 상세 페이지 |
| --- | --- |
| 폐쇄망 Kubernetes 이미지 패치 | `case-kubernetes-image-patch.html` |
| GitOps 배포 복구 | `case-gitops-recovery.html` |
| 폐쇄망 패치 실행 가이드와 기술지원 | `case-operations-guide.html` |

상세 페이지는 배기영 포트폴리오처럼 상단에서 프로젝트의 정체와 역할을 먼저 보여주고, 아래에서 문제와 해결 과정을 자료와 함께 읽게 한다. 시각 디자인은 현재 사이트의 글꼴, 색, 여백과 카드 규칙을 따른다.

1. **첫 화면:** 제목, 한 줄 설명, 실무 또는 개인 탐구, 맡은 범위, 확인된 기간과 사용 기술
2. **문제:** 어떤 환경에서 무엇이 막혔는지. 운영 제약과 재현 가능한 증상
3. **판단과 실행:** 본인이 확인한 단서, 선택한 조치, 다른 가능성을 어떻게 배제했는지
4. **증거:** 해당 단계 옆에 캡처, 로그, 설정, 코드 또는 문서 발췌를 배치
5. **검증:** 무엇을 확인했고 어느 상태까지 해결했는지. 수치가 없으면 만들지 않는다.
6. **다음 단계:** 진행 중인 작업에만 현재 한계와 다음에 시험할 내용을 적는다.

같은 순서의 세 칸을 모든 사례에 억지로 맞추지 않는다. 독자가 실제로 궁금해할 결정과 자료를 중심으로 각 페이지의 분량을 조절한다. 하단에는 Beyond Frontend 목록과 다음 사례 링크를 둔다.

## 현재 세 건을 깊게 만드는 방법

| 사례 | 상세에서 보여줄 핵심 | 확보할 자료 |
| --- | --- | --- |
| Kubernetes 이미지 패치 | 폐쇄망 제약, 이미지 반입과 교체 범위, 배포 검증, 롤백 판단 기준 | 이미지와 워크로드 상태의 식별값을 가린 캡처, 실행 가이드 일부 |
| GitOps 배포 복구 | Argo CD 저장소 연결 문제와 Harbor Pull 401을 분리한 진단, 조치 순서, 재배포 확인 | 오류 로그와 Argo CD 상태 화면의 식별값을 가린 캡처 |
| 패치 가이드와 기술지원 | 다른 작업자가 따라야 하는 순서, 사전 조건, 실패 시 대응, 보고서에 남긴 확인 항목 | 가이드 목차 또는 체크리스트, 기술지원 보고서 일부 |

세 번째 페이지가 문서 목차와 짧은 요약만으로 끝나지 않도록 실제 가이드의 구성과 판단 기준을 보여준다. 공개할 수 있는 자료가 부족하면 독립 카드로 부풀리지 않고 앞선 두 사례의 문서화 구역에 연결한다.

## 앞으로 추가할 작업

백엔드나 자동화 작업이 생기면 새로운 탭을 만들지 않고 Beyond Frontend 목록에 추가한다. `BACKEND`, `AUTOMATION`, `PLATFORM`, `DATA`는 카드의 작은 분야 표기로만 쓴다. `실무`, `개인 탐구`, `진행 중`은 작업의 성격을 알려주는 표기로 둔다.

새 항목을 올릴 때는 아래 네 가지가 있어야 한다.

- 본인이 해결하거나 시험한 구체적인 문제
- 직접 맡은 범위와 선택한 방법
- 코드, 실행 화면, 로그, 문서 중 확인 가능한 자료 한 가지 이상
- 완료 결과 또는 진행 중인 경우 현재까지 검증한 내용

이 규칙이면 Kubernetes 사례 뒤에 API 개발, 배포 자동화, 데이터 처리 작업이 추가돼도 두 번째 탭의 구조를 바꿀 필요가 없다.

## 적용 순서

1. 현재 세 건의 원본 자료와 본인 담당 범위를 확인하고 공개 자료의 식별값을 가린다.
2. 공통 상세 레이아웃을 만들고 현재 한 페이지의 세 구역을 각 페이지로 분리한다.
3. 목록 카드의 고정 번호와 반복 도식을 없애고, 각 사례의 자료와 독립 페이지를 연결한다.
4. 새 작업은 위의 네 가지 기준을 채웠을 때 같은 목록에 추가한다.

현재 브라우저에서 본 화면은 `legacy/html/index.html`이다. `react/`의 Next.js 사이트에는 이 두 번째 탭이 아직 없으므로, 실제 운영 사이트에 보이게 하려면 같은 구성으로 이식해야 한다.
