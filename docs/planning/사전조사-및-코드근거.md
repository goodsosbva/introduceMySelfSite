## 사용자 답변에서 확보한 내용

- 프론트엔드 직무를 목표로 하며 B2C를 선호한다.
- 개발 자체를 즐기고 배운 것을 실행하는 태도, 세부 동작을 신경 쓰면서 협업할 수 있는 성향을 보여주고 싶다고 답했다.
- 선호하는 형식은 짧은 경력 요약에서 실제로 상세한 구현 글로 이동하는 방식이다.
- 한국어 웹을 먼저 만들고 사진은 사용하지 않는다.

- 오케스트로에서는 모노레포 설정, 공통 컴포넌트, 다국어에 기여했다고 답했다.
- 공통 UI 이전에는 개발자에 따라 화면 형태와 기능 동작이 달랐고, 현재는 모든 팀이 공통 UI를 사용한다고 설명했다.
- 개발본부 규모는 약 60명, 총 5팀이라는 진술이다.
- 이 수치는 프론트엔드 인원이나 특정 컴포넌트의 실제 이용자 수를 의미하지 않는다.

- 다국어 라이브러리는 vue-i18n이며 한국어와 영어를 지원한다고 답했다.
- 적용 영역은 모니터링과 거버넌스다.
- 로그, 알람, 인프라 관리, 서비스 카탈로그, 자원 생성 폼과 커뮤니티 기능도 담당했다고 설명했다.
- 세부 기능의 개인 작성 범위와 운영 반영 시점은 별도 확인이 필요하다.

- Module Federation과 FSD는 실무 경험이라고 답했다.
- FSD는 CMP 3.0.5 모노레포 하위 디렉터리에 적용했다는 내용이다.
- RAG, LangChain과 OpenAI API는 실습 경험이다.
- MCP는 개발 작업 도구로 활용했다는 설명이다.
- Kubernetes, Prometheus, Grafana, Datadog, Jenkins 등은 얕게 다뤄본 경험으로 표현했다.
- 이들을 주력 프론트엔드 기술과 같은 깊이로 나열하지 않는다.

- Storybook과 문서 가이드를 제공했으며 남아 있는 테스트 코드가 본인 작업이라는 진술이 있다.
- 테스트의 실제 통과 여부나 조직 전체 테스트 체계의 운영 여부는 이 진술만으로 확정하지 않는다.
- 회사 코드는 공개할 수 없으며, 유사한 구조를 독립적으로 재구성해 설명하는 것은 가능하다고 답했다.

- 루트 package.json에서 pnpm 사용과 Nx 실행 명령을 확인했다.

- nx.json에는 Vite, Storybook, ESLint 등의 작업 플러그인과 빌드 캐시 설정이 있다.
- 대표 라이브러리는 shared API, common, UI, style이다.

- 관리자와 사용자 앱은 각각 service-admin-web과 service-user-web에 있다.
- infra의 package.json은 공통 API, 공통 로직과 UI를 workspace 의존성으로 참조한다.
- 모노레포에서 공유 패키지를 이용한다는 설명을 뒷받침한다.

- GitLab과 Bitbucket은 저장소 협업 도구이며 워크스페이스 연결이나 패키지 배포 방식 자체를 설명하지 않는다.
- 단독 도입, 빌드 시간 단축이나 독립 배포 달성을 추가할 근거는 없다.

### A02 Module Federation과 FSD 범위

- 관리자 앱의 Vite 설정은 federation 플러그인을 사용한다.
- 관리자 앱은 host로 동작하며 별도의 커스텀 remote를 등록하고 공통 UI, API와 common을 expose한다.
- Vue와 Vue Router 등의 공유 의존성에는 singleton 설정이 있다.
- remote 설정 여부에 따른 조건부 처리가 있고 프리뷰용 우회도 존재한다.

- 관리자와 사용자라는 두 앱이 존재하는 사실만으로 둘 사이를 Module Federation이 분리했다고 단정할 수 없다.
- 현재 설정이 직접 보여주는 것은 포털 앱과 커스텀 remote, 공유 모듈의 관계다.
- 당시의 추가 Webpack 버전이나 운영 토폴로지는 이 첨부본에서 확정하지 않았다.

- 모니터링과 거버넌스의 pages, widgets, features, entities, shared 디렉터리와 여러 index 진입점을 확인했다.
- 이것은 FSD에 맞춘 구획의 근거다.
- 공통 UI 전체는 form-elements, display, feedback 같은 별도 분류도 사용하므로 저장소 모든 영역이 동일한 FSD 구조라고 쓰지 않는다.
- 조사한 Nx와 ESLint 설정에서는 FSD 의존 방향을 자동 강제한다는 근거를 찾지 못했다.

- 근거: apps/service-admin-web/vite.config.ts 220부터 261행, apps/service-user-web/vite.config.ts, packages/monitoring/monitoring/project.json, 모니터링과 거버넌스의 src 디렉터리다.

- 데이터, 컬럼, 필터, 페이지 처리와 화면 조건을 받는다.
- 컬럼 타입에는 날짜, 숫자, 링크, 상태, 액션 등 표시 목적에 따른 구분과 숨김, 고정, 리사이즈 등의 설정이 있다.

### A04 공통 버튼과 Storybook

- CmpButton은 Ant Design Vue 버튼을 바탕으로 버튼 종류, 크기, 위험 표시, 비활성, 링크, 로딩, 선택 상태와 아이콘 속성을 받는다.
- 로딩 상태 자체와 화면에 로딩 아이콘을 표시하는 시점은 나뉘어 있다.

- 공통 Storybook 설정에는 Vue 3용 Vite 프레임워크와 docs, a11y addon이 있다.
- CmpTable과 CmpButton의 stories에서 사용 예와 속성 설명이 확인된다.
- a11y addon 설치는 접근성 인증이나 모든 화면 검증 완료를 의미하지 않는다.

### A06 로그 조회와 렌더링 범위

- useLogTableInfiniteQuery는 TanStack Vue Query의 useInfiniteQuery를 사용한다.
- 기간, 유형, 연동 대상, 이벤트명, 자원 구분, 키워드와 정렬을 Query 키에 포함한다.
- 요청 크기는 50이며 다음 페이지에는 마지막 항목의 ID와 timestamp를 전달한다.
- 페이지 응답을 합쳐 화면 데이터로 바꾸고 항목에는 markRaw를 적용한다.

- LogTable.vue는 Pinia 상태와 쿼리를 연결하고 useTableWindowing을 사용한다.
- 필터와 기간 등의 조합을 시그니처로 만들고, 조회 조건이 바뀔 때 남아 있는 스크롤 위치가 추가 요청을 연쇄 실행하지 않도록 초기화하는 처리가 있다.
- 스크롤 이벤트의 렌더링 범위 갱신은 requestAnimationFrame으로 묶는다.
- 같은 필터 배열이면 store ref를 다시 바꾸지 않는 처리도 있다.

- useTableWindowing은 기본 행 높이 36px와 앞뒤 버퍼를 전제로 표시 범위를 계산한다.
- 실제 행 일부와 위아래 spacer를 전달해 전체 높이를 유지한다.
- 로그 화면의 버퍼 값은 앞뒤 각각 100개다.
- 전체 조회 데이터를 메모리에서 폐기하는 처리는 아니므로 DOM 범위 제한과 메모리 사용량 제한을 혼동하지 않는다.
