## 1. 추천 방향

- 프로젝트 설명: **정책 근거를 검색하고 실제 화면과 코드를 분석해 테스트를 설계, 검증, 실행하는 AI QA 작업 도구**
- 기술 구성: **React + TypeScript / Python + FastAPI / LangChain + LangGraph / PostgreSQL + pgvector / Python Playwright**
- 사용자가 기존 구현 전체 교체를 허용했으므로 기존 Node 실행기와 산출물 형식을 호환해야 하는 조건을 해제
- 정책 수집, 검색, AI 판단, 계약 검증, 테스트 실행을 Python으로 구현
- 프론트엔드의 Node 기반 개발 도구와 대상 웹앱의 실행 환경은 별개. 제품 백엔드에 기존 Node 실행기를 연결하지 않음
- 기존 코드는 문제 사례와 요구사항을 확인하는 자료로 사용. 기존 Git 이력으로 이전 구현을 보존
- 첫 범위는 공개용 입력 폼과 해당 정책. 모든 웹앱을 자율 탐색하는 범용 에이전트는 후속 범위

## 3. 세 기술의 역할

| 기술 | 해결할 문제 | 구현 완료의 증거 |
|---|---|---|
| RAG | 관련 정책을 사람이 다시 찾는 부담과 근거 누락 | 검색한 문단이 계약과 테스트 기대값에 연결됨 |
| Function Calling | 필요한 정책과 코드 정보를 모델이 추가로 확인 | 모델의 tool call 요청을 서버가 검증 후 실행하고 결과를 모델에 반환 |

- 자동화 흐름 전체를 LLM에 맡기지 않고 검증과 테스트 실행은 고정 노드에서 수행
- 공식 근거: [Tools](https://docs.langchain.com/oss/python/langchain/tools), [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)

## 4. 첫 시연의 범위

- 대상 화면: 공개용 주문 등록 폼 한 개
- 입력: 주문명, 수량, 요청 금액, 메모
- 공개용 정책: 필수 여부, 길이, 숫자 범위, 소수점, 저장 후 반영에 대한 문서 5~10개
- 기본 시나리오: 주문명 최대 20자 정책으로 정상값, 20자, 21자, 빈 값, 공백 입력 설계
- 정책 버전 시나리오: 이전 20자 정책과 현재 30자 정책 중 적용할 버전을 구분
- 충돌 시나리오: 정책은 20자인데 별도 오류 fixture의 구현은 30자를 허용하도록 구성
- 근거 부족 시나리오: 통화 반올림 규칙을 문서에서 찾을 수 없으면 확인 대기
- 복구 시나리오: 확인 대기 중 서버를 재시작하고 같은 run ID로 재개
- 정상 폼과 오류 폼은 분리하고 실제 회사 서비스나 공용 배포 데이터에 테스트 쓰기를 하지 않음

### 시연 순서

1. 정책 문서를 등록하고 색인 결과 확인
2. 주문 등록 화면과 검사 목적 선택
3. 모델이 정책 검색과 관련 코드 확인 도구 호출
4. 정상, 실패, 경계 테스트 초안 생성
5. 각 기대값 옆에서 정책 제목과 원문 문단 확인
6. 정책 충돌은 사용자에게 근거와 함께 표시
7. 검증된 실행계획을 Python Playwright의 고정된 동작과 검증 함수로 실행
8. 실패 화면에서 정책, 코드, 테스트 결과의 연결 확인

## 5. RAG 상세 구현

### 저장할 정보

- 문서: 문서 ID, 제목, 프로젝트, 정책 버전, 적용일, 본문 해시
- chunk: 문서 ID, 제목 경로, 문단 위치, 원문 텍스트, 임베딩, 임베딩 모델 버전
- 계약 근거: chunk ID, 정책 버전, 인용 구간, 연결된 필드와 제약
- 실행: run ID, 대상 프로젝트와 라우트, 코드 버전, 정책 스냅샷, 계약 해시

### 검색 방식

1. 프로젝트와 적용 정책 버전으로 범위 제한
2. 필드 설명과 검사 목적을 검색 질문으로 구성
3. pgvector 유사도 검색으로 의미가 가까운 문단 조회
4. 필드명, 오류 코드, 숫자 조건은 키워드 일치 결과로 보완
5. 같은 문서의 중복 후보를 줄이고 필요한 부모 문단 포함
6. 검색 결과를 계약 생성 입력으로 전달하고 source ID를 강제

- 처음에는 작은 문서 집합에서 정확 검색으로 기준 성능을 측정
- 문서 규모와 검색 지연이 커졌을 때 HNSW 등 근사 색인을 비교
- pgvector는 Postgres 안에서 벡터 검색을 제공하므로 별도 벡터 DB 서버 없이 시작 가능. [공식 저장소](https://github.com/pgvector/pgvector)
- 원문에 있는 숫자와 예외를 생성 기대값과 비교하고 불일치 시 통과 처리하지 않음
- 문서에 없는 제약은 추측해서 추가하지 않고 근거 부족으로 분류
- 평가 질문 20개와 정답 문단을 준비해 기존 키워드 방식과 Recall@5, 근거 정확성을 비교
- 목표 수치와 실제 측정치를 구분해 보고서에 기록

## 6. Function Calling 상세 구현

### 모델에 제공할 도구

| 도구 | 입력 | 반환 | 용도 |
|---|---|---|---|
| `search_policy` | 질문, capability, 검색 개수 | 문단과 source ID, 버전, 점수 | 관련 정책 검색 |
| `read_project_file` | 허용된 파일 ID, 줄 범위 | 코드와 위치 | validation과 실제 컴포넌트 확인 |
| `inspect_page` | 사전 등록한 라우트 ID | 접근성 요소와 현재 화면 상태 | 코드에서 찾은 필드의 화면 존재 확인 |

- 프로젝트, 정책 버전, 접근 범위는 서버의 실행 상태에서 주입. 모델이 다른 프로젝트로 바꾸지 못하게 처리
- 도구 인자는 Pydantic으로 검증하고 파일과 라우트는 서버의 허용 목록에서 해석
- 서버는 호출 ID, 인자, 시작과 종료 시각, 결과 요약, 오류를 기록
- 도구 결과를 같은 호출 ID와 연결해 모델에 전달하고 다음 판단을 받음
- 초기 도구 호출 예산은 실행당 8회부터 시작하고 초과 시 보완 요청 또는 종료
- 모델에 임의 shell, SQL, 전체 파일 시스템 접근 기능을 제공하지 않음

### 호출 예시

```json
{
  "name": "search_policy",
  "arguments": {
    "query": "주문명 입력 길이와 필수값 정책",
    "capability": "input",
    "top_k": 5
  }
}
```

- 위 JSON은 설명용 예시. 실제 시연에서는 모델 응답의 tool call, 서버 실행, 결과 반환을 기록
- 계약 검증과 테스트 실행은 모델이 임의로 선택하는 도구 목록에 넣지 않고 graph의 고정 노드로 연결

## 7. LangGraph 상세 구현

| 노드 | 처리 | 다음 경로 |
|---|---|---|
| `prepare` | 대상과 정책 스냅샷 확정 | `analyze` |
| `analyze` | 도구 호출로 정책과 코드, 화면 확인 | `draft` 또는 근거 부족 |
| `draft` | 구조화된 계약과 근거 생성 | `validate` |
| `validate` | Pydantic과 Python 의미 검증 함수 실행 | 정상은 검토, 형식 오류는 보정, 정책 충돌은 확인 대기 |
| `repair` | 검증 오류에 한정해 계약 수정 | `validate`, 최대 2회 |
| `review` | 실행 대상과 계약 확인, 필요한 사용자 응답 대기 | `execute` 또는 보완 |
| `execute` | 검증한 실행계획을 Python Playwright로 실행 | `report` |
| `report` | 근거와 실행 결과, 비용과 시간 저장 | 완료 |

- `run_id`와 `thread_id`를 연결하고 Postgres 체크포인터 사용
- 체크포인트와 검색용 정책 chunk는 별도 테이블과 수명으로 관리
- `interrupt`로 확인 대기하고 같은 thread ID로 재개
- 확인 노드와 테스트 실행 노드를 분리해 재개 시 부작용 중복을 줄임
- 테스트 실행 시작과 완료 기록을 남기고 실행 여부가 모호하면 임의로 재실행하지 않음
- 첫 버전은 명시적인 재개 버튼으로 복구. 서버 재시작 후 자동 작업 재개는 다음 범위에서 설계
- 공식 근거: [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 8. Python 실행계획과 검증기 새로 구현

- 기본 산출물은 `test-plan.json` 하나로 구성하고 Pydantic으로 검증
- 모델은 임의 Python 실행 코드 대신 필드, 케이스, 동작, 기대값과 출처를 구조화해 생성
- Python 실행기는 허용된 동작과 assertion만 해석해서 실행
- 필드 목록, 커버리지, 결과 화면은 같은 실행계획에서 계산. 이전 구현의 여러 필수 YAML과 Markdown 파일을 그대로 만들지 않음

| 구조 | 저장할 내용 |
|---|---|
| `TestPlan` | 스키마 버전, 프로젝트와 라우트, 정책 스냅샷, 필드 목록, 케이스 |
| `Case` | 목적, 선행조건, 입력값, 동작, 기대값, 근거, 실행 가능 여부 |
| `Step` | fill, click, select, press 등 허용된 동작과 실제 확인한 locator |
| `Assertion` | value, text, visible, URL 등 허용된 검증과 기대값 |
| `EvidenceRef` | 정책 chunk 또는 코드 위치, 버전, 인용 구간 |

- 형식 검증: 필수값, 타입, 중복 ID, 허용된 동작과 assertion 검사
- 의미 검증: 실제 출처 존재, 정책 버전, 기대값 근거, 필드 참조, 정상과 실패 및 경계 케이스의 누락 검사
- 모르는 필드나 근거 부족 항목은 이유를 남기고 미검증으로 표시. 화면 전체를 검증한 것으로 요약하지 않음
- locator가 없거나 여러 요소와 일치하면 실행을 멈추고 보완. 임의 첫 요소를 클릭해 통과시키지 않음
- 실행별로 브라우저 context를 분리하고 실패 캡처, trace, 동작 및 검증 결과를 저장
- Python Playwright는 동기와 비동기 브라우저 자동화 API를 제공함. [공식 문서](https://playwright.dev/python/docs/intro)

### 새 구현 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 새 프로젝트와 데이터 구조 | React와 API 기동, DB 연결, 실행 ID와 실행계획 스키마 정의 |
| 2 | Python Playwright 실행기 | 사람이 작성한 실행계획으로 정상 폼 통과와 오류 폼 실패 확인 |
| 3 | 정책 RAG | 문서 등록, 분할, 임베딩, 버전 필터, 근거 검색 연결 |
| 4 | 도구 호출과 계약 생성 | 모델이 정책과 코드를 확인하고 유효한 실행계획 생성 |
| 5 | LangGraph | 보정, 확인 대기, 영속 체크포인트와 재개 연결 |
| 6 | React 작업 화면 | 실제 검색, 호출, 검토, 실행과 결과 표시 |
| 7 | 실패와 품질 평가 | 정책 충돌, 근거 부족, 오탐, 검색 누락과 재개 검증 |
| 8 | 배포와 제출 자료 | Docker 재현, 배포 시연, 문서와 영상 |

## 9. React 화면과 API

### 한 화면의 네 구역

1. 실행 대상과 상태: 프로젝트, 라우트, 정책 버전, 현재 단계
2. 근거: 검색 질문, 호출한 도구, 원문 문단, 코드 위치
3. 계약: 필드별 제약, 테스트 케이스, 누락과 정책 충돌
4. 결과: 통과와 실패, trace, 캡처, 비용, 소요 시간

### 최소 API

| API | 역할 |
|---|---|
| `POST /documents` | 공개용 문서 등록과 색인 |
| `POST /runs` | 등록된 대상에 새 실행 생성 |
| `GET /runs/{id}` | 현재 실행과 산출물 요약 |
| `GET /runs/{id}/events` | SSE로 단계와 도구 실행 이벤트 전달 |
| `POST /runs/{id}/resume` | 확인 응답 검증 후 재개 |

- 모델 텍스트만 스트리밍하지 않고 실제 노드 시작, 도구 실행, 검증 결과를 화면에 반영
- 새로고침 시 run ID로 실행 상태를 복구하고 이벤트 순서 ID로 중복 제거
- 첫 버전은 API 한 개와 DB 한 개로 시작. 별도 메시지 브로커와 대규모 worker 구조는 추가하지 않음
- Docker 시연 환경에는 Python Playwright와 Chromium의 브라우저 의존성 포함

## 10. 마감 전 범위와 후속 범위

### 마감 전: 작은 완성본을 목표로 하되 제출을 우선

| 순서 | 구현 범위 | 제출 가능한 증거 |
|---|---|---|
| 1 | Python API, 정책 샘플, Postgres와 임베딩 검색 | 검색 질문과 실제 근거 반환 |
| 2 | 정책 검색과 파일 읽기 tool calling | 실제 도구 호출 기록 |
| 3 | LangGraph 분석, 계약 생성, 검증과 보정 | 정상과 형식 오류의 실제 분기 |
| 4 | React 한 화면과 Python 실행기 연결 | 근거에서 실행 결과까지 이어지는 짧은 영상 |
| 5 | README와 지원 문구 정리 | 완료 범위, 남은 범위, 재현 방법 |

- 마감 전 모든 기능 완성을 확약하지 않음. 새 실행기와 모델 응답을 실제로 연결하는 작업이 가장 큰 변수
- 마감일에는 구현을 계속하느라 지원을 미루지 않음
- 미완성 기능은 진행 중으로 표시하고 실제 동작하는 범위를 제출
- 키와 연동 준비가 부족하면 기존 Common Tester 구현 근거와 후속 설계를 먼저 제출

### 면접 준비 단계: 약 2~3주를 가정한 확장

- 주 1: 실행계획 스키마와 Python 실행기, 정책 검색과 모델 생성 연결
- 주 2: 영속 체크포인트, 서버 재시작 후 재개, 실행 이력과 UI 완성
- 주 3: 검색과 테스트 품질 평가, Docker와 클라우드 배포, 실패 사례와 한계 정리
- 일정은 1인 작업량 초안이며 현재 숙련도, 모델 키 준비, 배포 환경에 따라 조정

## 11. 면접에서 설명할 질문과 증거

| 질문 | 설명과 준비할 자료 |
|---|---|
| RAG를 왜 적용했는가 | 기존 키워드 누락 사례와 새 검색 결과의 비교 |
| Function Calling을 어디에 썼는가 | 모델이 정책 검색 뒤 코드 확인을 선택한 실제 호출 기록 |
| LangGraph가 왜 필요한가 | 오류 보정, 확인 대기, 중단 후 재개의 같은 run 기록 |
| 환각을 어떻게 다뤘는가 | 없는 정책, 잘못된 source ID, 정책 충돌을 차단한 사례 |
| 테스트가 틀리면 어떻게 하는가 | 제품 오류, 생성 오류, 환경 오류를 구분하고 불확실한 결과를 남긴 사례 |
| 실행의 신뢰성을 어떻게 확보했는가 | 구조화된 실행계획, Python 검증기, 고정된 Playwright 동작의 경계 |
| 운영을 고려했는가 | 실행 시간, 모델 비용, 실패 로그, 키 보관, 재시작과 재개 기록 |
