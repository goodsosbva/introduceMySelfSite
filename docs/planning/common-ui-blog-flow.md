# 블로그 글 기획: 같은 제품인데 화면마다 달랐던 UI

## 연결할 포트폴리오

- Frontend → 공통 UI
- 블로그 글 제목: **같은 제품인데 화면마다 달랐던 UI, 공통 컴포넌트가 필요했던 이유**
- 글의 초점: 공통 UI가 필요했던 실제 화면의 차이, 공통화할 영역을 정한 기준, 다른 개발자가 사용하는 방법

## 먼저 사실관계 구분

사용자가 제공한 첫 세 장은 **공통 컴포넌트 구현 전** 화면이다. 리소스 상세, YAML 상세, 내용 상세에서 탭과 소제목, 본문 시작 위치가 서로 다르다.

이번에 제공한 두 장은 **변경 후** 화면이다. 알람 정책 목록에는 필터, 요약 수치, 검색, 작업 버튼, 테이블, 페이지네이션이 보인다. 업무 라벨 상세에는 상단 작업 버튼, 좌측 기본 정보, 탭, 검색, 테이블, 페이지네이션이 보인다. 실제 서비스 화면도 확인했다.

전후 자료는 동일한 화면의 같은 위치를 찍은 쌍이 아니다. 따라서 `이 화면이 정확히 이렇게 바뀌었다`는 식의 전후 비교로 사용하지 않는다. 구현 전 화면은 **왜 기준이 필요했는지**, 변경 후 화면은 **여러 화면에 적용된 UI 구성의 모습**을 보여주는 근거로 사용한다.

## 글의 핵심 문장

> 같은 제품의 상세 화면인데 탭 아래 소제목의 유무와 여백이 화면마다 달랐다. 화면을 각각 만들면 같은 역할의 영역도 조금씩 달라진다. 공통 UI 작업은 반복되는 영역의 기준을 한곳에 두고, 각 화면은 필요한 내용을 채우도록 하기 위한 일이었다.

## 글 전개

### 1. 구현 전 화면 세 장으로 문제를 보여준다

글의 첫 화면에 세 사례를 나란히 **직접 그린 도식**으로 배치한다.

| 화면 | 도식에서 강조할 부분 |
| --- | --- |
| 리소스 상세 | 탭 아래 `컨테이너`, `볼륨`, `상태` 소제목이 여러 번 등장한다. |
| YAML 상세 | 탭 아래 `Values.yaml` 제목과 편집기가 이어진다. |
| 일반 내용 상세 | `내용` 탭 다음에 별도 소제목 없이 본문이 시작된다. |

탭 높이, 소제목 자리, 본문 시작선과 좌우 여백에 표시선을 그린다. 제목 유무 자체는 화면 내용의 차이일 수 있으므로 무조건 오류라고 쓰지 않는다. **제목이 있을 때와 없을 때의 영역 처리 기준이 통일되지 않았다는 점**을 문제로 적는다.

도입 문장 예시:

> 화면마다 담는 정보는 다를 수 있다. 그런데 같은 제품 안에서 탭과 본문이 만나는 위치까지 매번 다르게 보였다. 한 화면에서는 탭 아래에 소제목이 반복되고, 다른 화면에서는 파일명이 제목이 되며, 또 다른 화면에서는 제목 없이 내용이 시작됐다. 화면을 각각 구현하면서 공통으로 적용할 레이아웃 기준이 필요해졌다.

### 2. 무엇을 공통으로, 무엇을 화면별로 두었는지 설명한다

공통 컴포넌트의 범위는 실제 구현 자료로 확인한 것만 단정해서 쓴다. 현재 포트폴리오 상세에 기록된 본인 기여는 **테이블과 버튼 개발 및 개선, 모노레포 설정과 패키지 분리 참여, Storybook 사용 가이드 제공**이다. 탭 전체나 모든 필터를 직접 개발했다고 확대하지 않는다.

이 절에서는 개념을 다음처럼 구분한다.

| 공통으로 관리할 기준 | 각 화면이 결정할 내용 |
| --- | --- |
| 반복되는 컴포넌트의 기본 모양과 사용 방법 | 소제목 문구와 표시 여부 |
| 테이블의 기본 표시, 페이지네이션, 데이터 없음 상태 | 컬럼 구성과 표시할 데이터 |
| 버튼의 공통 규격과 상태 표현 | 버튼 문구와 클릭 시 실행할 업무 동작 |
| 재사용 가능한 셀 표현 방식 | 해당 화면의 상태값과 표현 조건 |

정렬 규칙과 조회 조건은 업무 화면의 데이터 처리에 속한다. `정렬 로직까지 공통 컴포넌트로 해결했다`고 쓰지 않는다. 화면별 컬럼과 버튼 차이도 공통화 실패로 취급하지 않는다. 각 화면이 데이터를 전달하거나 필요한 표현을 넣을 수 있어야 재사용할 수 있다는 설명으로 연결한다.

### 3. 다른 개발자가 어떻게 사용하는지 보여준다

공통 컴포넌트의 내부 코드를 열어보지 않아도 사용할 수 있도록 정리한 **Storybook 사용 가이드**를 실제 자료로 보여준다.

전개 순서:

1. Storybook에서 필요한 컴포넌트와 기본 예시를 찾는다.
2. 속성과 사용 예를 보고 화면에 맞는 데이터와 설정을 전달한다.
3. 화면별 표현이 필요한 자리는 제공된 확장 지점을 사용한다.
4. 공통 컴포넌트 자체를 수정해야 하는 경우와 화면 코드만 수정하면 되는 경우를 구분한다.

기존 포트폴리오 상세에는 테이블에 `data`, `columns`를 전달하고 `bodyCell` 슬롯에 상태 태그를 넣은 예시가 있다. 블로그에 코드를 실을 때는 **실제 프로젝트에서 사용한 API 이름과 코드**를 확인해 반영한다. 기획용 도식의 임의 코드나 추측한 속성은 게시하지 않는다.

### 4. 변경 후 화면에서 적용 모습을 보여준다

두 변경 후 화면도 실제 캡처를 그대로 싣지 않고, 구성 요소를 단순화해 다시 그린다.

- **알람 정책 목록 도식:** 좌측 필터, 상단 요약, 검색과 작업 버튼, 테이블, 하단 페이지네이션을 표시한다.
- **업무 라벨 상세 도식:** 상단 제목과 작업 버튼, 좌측 기본 정보, 우측 탭, 검색, 테이블, 하단 페이지네이션을 표시한다.

이 절의 문장은 `같은 컴포넌트가 두 화면의 모든 부분을 만들었다`가 아니다. **서로 다른 업무 화면에서도 반복되는 UI 영역과 사용 규칙이 보인다**는 수준으로 쓴다. 직접 담당한 부분은 앞 절에 명시한 범위로 한정한다.

설명 문장 예시:

> 알람 정책 목록과 업무 라벨 상세는 화면 목적이 다르다. 그래도 검색, 버튼, 표와 페이지 이동처럼 반복되는 요소가 있다. 공통 UI는 이런 요소를 매번 새로 만들지 않고 같은 기준으로 사용할 수 있게 한다. 각 화면의 데이터와 작업은 해당 화면에서 결정한다.

### 5. 확인 가능한 내용으로 끝맺는다

결론에서는 `개발 시간 N% 단축`, `버그 감소`, `모든 화면의 일관성 확보` 같은 측정하지 않은 결과를 쓰지 않는다. 화면과 문서로 확인 가능한 내용만 남긴다.

> 공통 UI 작업은 모든 화면을 똑같게 만드는 일이 아니었다. 반복되는 부분의 기준과 사용법을 정리하고, 각 화면이 필요한 정보와 동작을 넣을 자리를 남기는 일이었다. Storybook에 예시와 사용법을 두어 다른 개발자가 내부 구현을 파악하는 데 시간을 쓰지 않고 화면에 적용할 수 있게 했다.

## 게시용 그림 제작 지침

1. **Before 비교 그림:** 세 기존 화면의 탭과 소제목 관계만 다시 그린다. 서로 다른 시작선과 여백을 표시한다.
2. **공통화 범위 그림:** 바깥 공통 영역과 화면별 콘텐츠를 다른 색으로 나눠 표시한다. 실제 구현 범위로 확인된 부분만 `내가 개발`이라고 표기한다.
3. **After 구성 그림:** 알람 정책 목록과 업무 라벨 상세의 구조를 추상화한다. 실제 서비스의 항목명, 계정, 조직명, 자원명, 주소, 수치는 사용하지 않는다.
4. **사용 예 그림:** 실제 Storybook 화면을 참고해 컴포넌트 미리보기, 속성, 사용 순서를 다시 그리거나 공개 가능한 문서 부분만 사용한다.

그림은 `서비스 화면의 구조를 재구성한 도식`이라고 표시한다. 실제 캡처처럼 보이게 가짜 데이터와 상태를 정교하게 꾸며 결과로 제시하지 않는다.

## 게시 전 확인할 자료

- 실제 공통화한 컴포넌트 이름과 본인의 담당 범위
- Storybook의 실제 사용 예와 속성 이름
- 화면별 컬럼과 셀 표현을 연결한 실제 코드 한 조각
- 변경 후 두 화면 중 본인이 직접 적용하거나 개선한 영역

이 네 가지를 확인한 뒤에만 구현 방식과 결과를 확정 문장으로 쓴다.
