## 4. CityWatch의 실제 구성안

### 4-1. 핵심 사용 시나리오

1. 집중호우 시나리오를 선택해 시연 데이터 시작
2. 지도 영역과 심각도 필터로 대응이 필요한 사고 확인
3. 목록 또는 지도에서 사고 선택
4. 같은 화면의 상세 패널에서 담당 팀 배정과 출동 처리
5. 처리 사유와 현장 메모를 타임라인에 기록
6. 다른 브라우저에 변경 사항 반영
7. 사고 종결 후 대응 시간과 미처리 현황 확인

### 4-2. 화면 구성

| 화면 | 구성 | 사용자가 하는 일 |
|---|---|---|
| 관제 작업 화면 | 상단 요약, 좌측 사고 목록, 중앙 지도, 우측 상세 패널 | 필터링, 지도 선택, 담당 배정, 상태 변경 |
| 사고 상세 주소 | 동일한 상세 기능과 전체 처리 타임라인 | 특정 사고 공유, 이력 확인 |
| 분석 화면 | 기간별 접수와 종결 추이, 대응 소요 시간, 지역별 분포 | 지연 원인과 사고 집중 구간 확인 |
| 시연과 기술 보기 | 시나리오 시작과 초기화, X-Ray, 코드 실습, 성능 비교 | 구현 확인과 재현 |

- 데스크톱: 목록, 지도, 상세를 함께 표시
- 작은 화면: 목록과 지도 전환, 상세는 드로어로 표시
- 로딩, 빈 목록, 검색 결과 없음, 저장 실패, 연결 끊김, 충돌 상태를 각각 표시
- 데이터가 오래된 경우 마지막 갱신 시각과 재연결 상태 표시
- 기술명과 파일 경로는 개발자 보기에서 확인

### 4-3. 구현 순서와 기술 선택

| 순서 | 변경 | 기술과 구현 방식 | 선택 이유 |
|---|---|---|---|
| 1 | 사고와 이력 저장 | 기존 Next API + PostgreSQL | 현재 API를 유지하면서 데이터 일관성 확보 |
| 2 | 수정 충돌과 상태 전이 | 사고 `version`, 서버 전이 규칙, 409 처리 | 복수 사용자의 동시 수정과 잘못된 전이 처리 |
| 3 | 서버 데이터 공유 | 기존 Redux Toolkit의 RTK Query | 별도 상태 관리 도구를 추가하지 않고 조회와 변경 캐시 연결 |
| 4 | 실제 변경 이벤트 | 같은 DB 트랜잭션에 이벤트 저장, 기존 Node 서버가 전달 | 데이터 변경과 이벤트 사이 누락 방지 |
| 5 | 관제 화면 연결 | 기존 OpenLayers, 가상 목록, 상세 기능 재사용 | 기존 구현을 사용자 작업 흐름으로 통합 |
| 6 | 공유 가능한 조회 상태 | URL에 검색 조건, 기간, 지도 범위, 선택 사고 반영 | 새로고침, 뒤로 가기, 링크 공유 지원 |
| 7 | 분석 고도화 | 기존 Federation remote에 기간별 집계 연결 | 원격 모듈이 독립적인 분석 역할을 맡도록 구성 |

- RTK Query는 데이터 조회, 캐시, 변경 이후 갱신과 스트리밍 갱신을 지원함. [공식 문서](https://redux.js.org/toolkit/rtk-query/overview)
- DB 변경 후 이벤트를 별도 요청으로 전송하는 방식은 피하고, 사고와 이벤트를 함께 저장
- 이벤트 전달 실패는 재시도하고 클라이언트는 이벤트 ID와 사고 버전으로 중복 처리 방지
- WebSocket 유지가 가능한 기존 Node 배포를 활용. Next API와 연결할 DB 및 접속 설정을 배포 환경별로 정의
- 상태 변경 직후 해당 사고 캐시를 갱신하고 실패 시 되돌림. 목록 포함 여부나 집계가 달라지면 관련 쿼리를 무효화해 재조회
- 지도 영역 조회는 요청 지연 처리와 이전 요청 취소 적용
- 새 시연 데이터는 최소 수십 건의 서로 다른 상태와 이력으로 구성. 대량 부하 데이터는 기존 5천 건과 1만 건 시나리오 유지
- 시연 데이터는 세션별로 분리해 다른 방문자의 조작과 섞이지 않도록 구성
- 분석 모듈 로딩 실패 시 핵심 관제 작업은 계속 가능하도록 오류 경계와 재시도 제공
- 기존 3D 화면은 선택한 사고의 상세 보기로 연결. 재난 확산 예측처럼 실제로 계산하지 않는 의미를 부여하지 않음

### 4-4. 첫 구현의 완료 기준

- 사고 생성 → 목록과 지도 표시 → 배정 → 상태 변경 → 종결 → 이력 확인을 한 흐름으로 시연
- 두 브라우저의 상태 변경이 새로고침 없이 반영
- 서버 재시작 이후 사고와 이벤트 이력 유지
- 충돌, 저장 실패, 재연결 상황을 화면에서 구분
- 필터와 선택 사고가 URL로 복원
- 첫 화면에서 사용자가 수행할 작업과 현재 대응 상황을 파악 가능

## 5. Common Tester에서 확인한 문제

### CT-01. 검색이 키워드 분류와 점수 정렬에 의존함 — P1

- 근거: [분류](D:/common_tester/docs/tools/common-tester/operators/classify-policy-units.ts:50), [후보 선택](D:/common_tester/docs/tools/common-tester/operators/build-policy-candidates.ts:121)
- 현재: taxonomy 키워드가 포함되는지 검사하고 점수를 합산함. 분류되지 않은 단위는 후보 목록에서 제외됨
- 발생 조건: 같은 정책이 다른 표현으로 작성되거나 새로운 용어가 등장함
- 영향: 관련 정책이 추천 후보에 들지 못할 수 있음

### 6-2. RAG가 담당할 일

| 단계 | 입력 | 처리 | 남기는 결과 |
|---|---|---|---|
| 수집 | 로컬 정책 또는 Confluence | 문서 버전과 본문 해시 확인 | 문서 ID, 버전, 수집 시각 |
| 분할 | 정규화된 문서 | 제목, 표, 예외 조건을 보존하며 분할 | chunk ID, 부모 문단, 위치, 원문 해시 |
| 색인 | 정책 chunk | 키워드 색인과 임베딩 저장 | 문서별 색인 버전, 임베딩 모델 버전 |
| 검색 | 필드, 기능, 라우트, 정책 질문 | 프로젝트와 정책 버전 필터 후 키워드 및 의미 검색 결합 | 후보, 점수, 검색 조건 |
| 설계 | 검색 근거와 프로젝트 코드 | 제약과 정상, 실패, 경계 케이스를 구조화 | 계약, 출처, 불확실한 항목 |
| 검증 | 계약과 검색 근거 | 실제 존재하는 근거인지, 값과 조건이 일치하는지 검사 | 통과, 근거 부족, 충돌 |

- 시작은 검색 후 계약을 생성하는 2단계 RAG로 구성
- 문서 전체를 매번 넣는 비용을 줄이고 근거별로 계약과 테스트를 연결
- 정책 검색 결과만으로 화면 요소를 추측하지 않음. 실제 프로젝트 코드와 브라우저 확인을 함께 사용
- 모든 기대값에 정책 근거 또는 프로젝트 동작 근거를 표시하고 근거 유형을 구분
- 검색에 걸리지 않은 정책을 삭제하지 않음. 재검색과 전체 문단 확인 경로 유지
- 프로젝트 분석 노드는 라우트, 연결된 컴포넌트, validation, i18n 파일을 읽고 파일 경로와 줄 위치를 반환. Vue 전용 탐색기를 모든 프로젝트에 공통 적용하지 않음
- 모델에는 검색된 정책과 관련 코드 구간을 전달하고 스키마에 맞는 계약 초안을 응답받음. 파일 읽기와 브라우저 관찰 도구의 허용 범위와 호출 횟수 제한
- 내용이 바뀐 문서만 재색인하고 삭제 문서는 검색 결과에서 제외
- 문서의 명령형 문장을 도구 실행 지시로 사용하지 않음. 정책은 분석 자료로 취급
- 로컬 정책 샘플로 먼저 구현. 외부 모델 사용 시 전달할 코드와 문서 범위를 설정에서 명시
- 검색과 생성이 결합되어야 RAG 도입이 완료된 것으로 판단. [공식 Retrieval 문서](https://docs.langchain.com/oss/javascript/deepagents/retrieval)

### 6-3. LangGraph가 담당할 일

1. 대상 프로젝트와 실행 정보 확정
2. 정책 수집과 색인 최신화
3. 프로젝트 코드와 실제 화면 분석
4. 관련 정책 검색
5. 계약 초안 생성
6. 기존 검증기로 형식, 참조, 커버리지 검사
7. 근거 부족 또는 정책 충돌 시 보완 검색이나 사용자 확인 대기
8. 검증된 계약을 Playwright 코드로 렌더링
9. 실행 목록과 런타임 확인
10. 테스트 실행
11. 실패 원인 분류와 리포트 저장

| 상황 | 분기와 제어 |
|---|---|
| 계약 형식 오류 | 오류 항목을 입력으로 초안 보정. 자동 보정은 최대 2회부터 시작 |
| 검색 근거 부족 | 질문을 보완해 재검색. 그래도 부족하면 근거 부족으로 종료 |
| 정책과 코드 충돌 | 근거를 나란히 표시하고 확인 대기. 현재 구현에 맞춰 성공 기대값으로 바꾸지 않음 |
| 일시적인 모델 또는 네트워크 오류 | 제한된 재시도와 대기 시간 적용 |
| 테스트 실패 | 제품 오류, 테스트 설계 오류, 실행 환경 오류, 정책 충돌로 분류. 확정 불가 상태 지원 |
| 실행 중 프로세스 종료 | 같은 run ID의 체크포인트와 실행 영수증을 읽어 재개 |

- graph 상태: project ID, target ID, run ID, 정책 버전, 검색 근거 ID, 계약 버전, 단계 상태, 오류, 비용
- `thread_id`는 run ID로 사용하고 대상 식별자는 별도 메타데이터로 보관
- 로컬 CLI는 SQLite 기반 영속 체크포인터 사용. 메모리 체크포인터만으로 재시작 복구를 구현했다고 표시하지 않음
- 원문 전체와 이미지 대신 필요한 ID, 요약, 산출물 경로 중심으로 체크포인트를 구성
- 검증을 통과한 설정과 계약은 실행 시작 후 고정하고 해시 기록
- 재개 시 같은 파일을 중복 생성하거나 같은 테스트를 무조건 다시 실행하지 않도록 단계별 입력 해시와 완료 기록 확인
- 브라우저에서 이미 발생한 쓰기 작업은 체크포인트만으로 정확히 한 번 실행을 보장할 수 없음. 실행 중단이 모호하면 결과 확인 또는 초기화된 시연 환경에서 명시적 재실행
- 승인 대기 노드와 파일 생성, 테스트 실행 노드는 분리. 재개 시 노드가 다시 실행될 수 있으므로 부작용의 중복 방지 필요. [Interrupts 공식 문서](https://docs.langchain.com/oss/javascript/langgraph/interrupts)
- 체크포인트는 실행 상태 저장용이고 정책 검색 색인은 별도 저장 구조로 관리. [Persistence 공식 문서](https://docs.langchain.com/oss/javascript/langgraph/persistence)

### 6-4. 최소 기술 구성

| 영역 | 제안 | 적용 범위 |
|---|---|---|
| 실행기 | 기존 Node.js + TypeScript | 기존 operator를 graph node에서 호출할 수 있도록 정리 |
| 흐름 제어 | `@langchain/langgraph` | 상태, 분기, 체크포인트, 중단과 재개 |
| 모델 호출 | 구조화 출력을 지원하는 모델 제공자 1개 | 계약 초안과 제한된 보정에 사용 |
| 검색 | SQLite FTS5 + 임베딩 유사도 검색 | 로컬 정책 샘플과 소규모 문서 집합부터 시작 |
| 검색 저장 | SQLite에 chunk, 메타데이터, 임베딩 저장 | 초기에는 앱에서 유사도 계산. 검색 시간 측정 후 전용 색인 도입 여부 결정 |
| 스키마 | 표준 YAML 파서 + Zod 등 런타임 스키마 | 형식 검사와 기존 의미 검증을 함께 적용 |
| 실행 | 기존 Playwright 렌더러와 runner 재사용 | 모델이 임의 실행 코드를 직접 만드는 범위 최소화 |
| 결과 화면 | React + TypeScript 작업 화면 | 안정된 CLI 위에 실행 관찰과 검토 기능 제공 |

- LangGraph 도입을 위해 Python으로 전면 재작성할 필요 없음
- 벡터 DB 서버, Redis, 메시지 브로커, 여러 에이전트 역할은 첫 구현에 추가하지 않음
- 기존 CLI `create`, `continue`, `summary`는 호환 진입점으로 유지하고 내부 실행 상태를 새 구조로 이전
- 대상 프로젝트 루트, 도구 설정 루트, 산출물 루트를 분리해 다른 프로젝트를 도구 저장소에 복사하지 않고 분석 가능하게 구성

### 6-5. 사용자가 보는 작업 화면

| 구역 | 표시 내용 | 가능한 작업 |
|---|---|---|
| 실행 목록 | 대상 프로젝트, 라우트, 정책 버전, 실행 결과 | 실행 선택, 새 실행 |
| 진행 상태 | 현재 단계, 소요 시간, 재시도, 확인 대기 사유 | 중단, 재개, 확인 응답 |
| 근거 패널 | 검색 질문, 후보 문단, 점수, 원문 위치 | 원문 확인, 추가 검색 |
| 계약 검토 | 필드와 제약, 정상 및 실패 케이스, 누락과 충돌 | 근거 보완, 계약 버전 비교 |
| 결과 패널 | 테스트 결과, 실행 환경 오류, trace, 화면 캡처 | 실패 근거 확인, 재실행 범위 선택 |

- 화면의 단계 상태는 실제 LangGraph 실행 이벤트를 사용
- 검색 결과 선택 시 연결된 필드, 계약, 테스트 케이스를 함께 강조
- 성공 건수만 표시하지 않고 근거 부족, 정책 충돌, 실행 안 됨 상태를 구분
- UI 개발은 검색과 실행 재개가 CLI에서 연결된 다음 진행

## 7. 두 프로젝트를 함께 보여주는 시연

1. CityWatch 사고 등록 폼에 대한 공개용 정책 문서 준비
2. Common Tester가 입력 필드와 정책을 연결
3. 정상, 필수값 누락, 경계값 케이스의 근거 확인
4. 계약과 테스트 생성 후 CityWatch의 분리된 시연 환경에서 실행
5. 의도적으로 제한값을 바꾼 별도 fixture에서 정책 불일치 탐지
6. 검사 도중 중단 후 같은 실행을 재개하고 이전 결과 유지 확인
7. 결과에서 원문 정책 → 계약 → 테스트 → 실패 화면까지 연결해서 제시

- 기존 배포 사이트나 다른 사용자의 데이터를 테스트 대상으로 변경하지 않음
- 이 시연에서 CityWatch는 복잡한 프론트엔드 상태와 상호작용을, Common Tester는 근거 기반 테스트 설계와 실행 제어를 보여줌

## 8. 실행 계획표

| 단계 | 작업 | 결과물 | 선행 조건 | 예상 작업량 |
|---|---|---|---|---|
| 0 | 현행 동작과 시연 데이터 기준 고정 | 화면 목록, 데이터 모델, 대표 시나리오 | 현재 분석 | 1일 |
| 1 | CityWatch 저장, 이력, 상태 전이, 이벤트 연결 | 일관된 API와 실시간 반영 | 0 | 3~5일 |
| 2 | CityWatch 관제 작업 화면과 URL 상태 | 지도, 목록, 상세가 연결된 시연 | 1 | 3~5일 |
| 3 | Common Tester 실행 의존성과 대상 및 실행 ID 정리 | 재현 가능한 CLI와 독립 실행 디렉터리 | 0 | 1~2일 |
| 4 | 정책 RAG와 계약 근거 연결 | 검색 색인, 인용, 정책 충돌 결과 | 3 | 3~5일 |
| 5 | LangGraph, 체크포인트, 재개와 실패 처리 | 중단과 재개가 가능한 실행기 | 4 | 3~5일 |
| 6 | Common Tester 실행 및 근거 화면 | 실제 실행 이벤트와 연결된 작업 화면 | 5 | 3~5일 |
| 7 | 두 프로젝트 통합 시연과 결과 기록 | 재현 가능한 시연과 포트폴리오 자료 | 2, 6 | 2~3일 |

- 전체 핵심 범위: 1인 기준 약 19~31 작업일의 초안 추정. 모델 제공자 연동, 배포 제약, 기존 계약 호환 범위에 따라 조정
- CityWatch 기간 분석 고도화와 실제 조회 부하 최적화는 핵심 시연 이후 P2로 진행
- 첫 구현 순서: CityWatch의 사고 한 건 처리 흐름 완성 → Common Tester의 입력 폼 한 종류 완성 → 공통 기능 확대
- 단계마다 결과를 확인한 뒤 다음 범위를 확대. 예상 일수는 납기 확약이 아님

## 9. 향후 검증 기준

### CityWatch

- 재시작 이후 사고와 처리 이력 유지
- 동시 변경 충돌과 저장 실패 시 UI 복구
- WebSocket 단절, polling 전환, 재연결, 누락 구간 복구
- 지도와 목록과 상세의 같은 사고 상태 일치
- URL을 통한 필터와 선택 상태 복원
- 키보드 접근, 패널 포커스 복귀, 작은 화면 사용성 확인
- 대량 조회와 화면 렌더링을 구분해 측정. 측정 전 성능 개선 비율을 경력 문구에 사용하지 않음

### Common Tester

- 실제 공개용 정책 질문 20~30개에 정답 문단을 지정해 기존 키워드 방식과 새 검색 비교
- 초기 검색 목표: 정답 근거 Recall@10 90% 이상. 목표치이며 현재 측정 결과는 아님
- 생성 계약의 출처 ID와 버전이 실제 색인 자료에 존재하는지 검사
- 인용이 존재하더라도 의미가 맞는지는 별도 표본 검토. 출처 존재 검사만으로 정확성을 보장하지 않음
- 정책이 부족하면 근거 부족, 정책과 구현이 다르면 충돌로 표시
- 알려진 오류를 넣은 별도 fixture에서 탐지 여부와 정상 fixture의 오탐을 함께 기록
- 단계별 중단과 재개, 실행 식별자 충돌, 실패 리포트 저장을 검증
- 실행별 모델명, 토큰 사용량, 비용, 지연 시간, 정책과 코드 버전을 기록

## 10. 이번 분석에서 확인하지 않은 범위

- 패키지 설치, 빌드, 단위 테스트, E2E 실행 결과
- 실제 배포 DB, 서버 인스턴스 구성, 운영 로그, GitHub Actions 실행 결과
- 유료 모델 호출 품질과 비용, 임베딩 모델별 한국어 정책 검색 정확도
- 비공개 Confluence 자료와 회사 코드의 외부 반출 허용 범위
- 전체 코드의 보안 감사와 모든 화면의 회귀 검증

## 11. 구현 후 경력기술서에 남길 내용

- CityWatch: 지도와 목록의 선택 상태, 서버 캐시, 실시간 이벤트를 연결하고 동시 변경과 연결 복구를 처리한 과정
- CityWatch: 대량 데이터의 API 조회와 렌더링 병목을 구분해 측정하고 개선한 결과
- Common Tester: 정책 문서를 검색 가능한 단위로 색인하고 RAG 근거를 테스트 계약과 연결한 과정
- Common Tester: LangGraph의 영속 상태와 분기로 중단, 재개, 근거 부족, 정책 충돌을 처리한 과정
- 공통: 실제 구현과 측정이 끝난 항목만 완료형으로 작성
