02 / CASE 01 / CMP TABLE

컬럼을 다시 잡을 때, 갑자기 튀지 않게

공통 테이블의 컬럼을 줄였다 늘린 뒤, 다음 드래그에서 폭이 갑자기 달라지던 문제를 다뤘습니다.

문제 원인

컬럼 상태에 저장된 너비와 브라우저가 가용 공간과 폭 제약을 적용해 그린 헤더 너비가 달랐습니다. 다음 드래그가 화면에 보이는 폭이 아닌 이전 상태값에서 시작해 컬럼이 튀었습니다.

02 DOM 실측

03 제약 보정

최소, 최대 폭 범위에 맞춤

04 동시 반영

colgroup과 컬럼 상태

재현 조건

가용 폭, 고정 컬럼, 선택 컬럼, 액션 컬럼과 최소, 최대 폭 제약이 함께 적용되면 선언한 너비와 실제 헤더 너비가 달라졌습니다.

해결 판단

상태값만 다시 계산해서는 브라우저가 분배한 폭을 알 수 없었습니다. 마지막 헤더 행의 실측 너비를 기준으로 삼았습니다.

바뀐 동작

측정한 폭을 보정해 상태와 colgroup에 함께 반영했습니다. 다음 드래그가 화면에 보이는 너비에서 시작됩니다.

const widths = headerCells.map((th) => th.getBoundingClientRect().width);
applyDomMeasuredWidthsToAllCols(columns, colgroup, widths, state);

03 / CASE 02 / DATA LIFECYCLE

화면은 남기고, 보이지 않는 요청만 멈추기

KeepAlive로 보관된 로그 화면이 창 포커스 복귀 시에도 API 요청을 이어가던 상황입니다.

문제 원인

KeepAlive가 로그 화면을 제거하지 않아 Query 구독자가 남아 있었습니다. 화면이 보이지 않아도 창 포커스 복귀 시 재조회가 실행됐습니다.

시도 후 되돌림

전역 refetchOnWindowFocus: false는 보이는 로그 화면의 포커스 복귀 최신화도 중단시켜 되돌렸습니다.

화면 생명주기

onActivated / onDeactivated

활성 상태 저장

Pinia의 isLogPageActive

Query 요청 권한

enabled에 활성 상태 연결

인시던트 화면

숨은 로그 요청은 멈추고, 현재 화면의 포커스 재조회는 유지합니다.

로그 화면 복귀

보관된 캐시를 먼저 보여주고, stale 상태라면 다시 조회합니다.

판단의 기준

캐시 존재 여부와 현재 화면의 요청 권한을 분리했습니다.

onActivated(() => logStore.setLogPageActive(true));
onDeactivated(() => logStore.setLogPageActive(false));
useQuery({ enabled: computed(() => logStore.isLogPageActive) });

04 / CASE 03 / ERROR CONTAINMENT

한 화면의 오류가 앱 전체를 멈추지 않게

Vue에는 바로 사용할 수 있는 내장 Error Boundary 컴포넌트가 없어, 페이지 단위 경계를 직접 구현했습니다.

문제 원인

하위 컴포넌트의 렌더링 오류가 부모 방향으로 전파되는데, 페이지 안에서 오류를 멈출 경계가 없어 RootLayout과 공통 내비게이션까지 영향을 줄 수 있었습니다.

APP / RootLayout + 공통 내비게이션
직접 구현한 ERROR BOUNDARY

하위 화면의 오류와 발생 맥락을 보관

전파 중단

공통 레이아웃까지 번지는 경로를 차단

01 포착

Vue의 onErrorCaptured로 하위 컴포넌트 오류와 발생 맥락을 받아 오류 상태로 보관합니다.

02 격리

오류 전파를 멈춰 한 페이지의 실패가 RootLayout과 공통 내비게이션에 영향을 주는 경로를 차단합니다.

03 회복

경로가 바뀌면 오류 상태를 초기화해 이전 화면의 실패가 다음 화면에 남지 않게 합니다.
